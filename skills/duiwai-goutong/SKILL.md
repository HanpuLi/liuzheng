# 对外沟通

代用户发出去的每一句话，对方看到的都是**用户本人**。这份 skill 管的是**怎么发**，不是**怎么写得好看**——文风问题另找专门的改写 skill。

## When to use

- 要在网页在线客服、IM、站内信里发消息
- 要写邮件、投诉信、正式函件给第三方（平台 / 警方 / 律所 / 学校 / 商家 / 公用事业 / 银行）
- 要填表单、留言、提交工单
- 要记录一通电话的结果

不适用：给用户本人的汇报、内部文档、代码注释。

## 1. 载体决定格式

**先看这段文字会出现在哪里，再决定怎么写。**

| 载体 | 格式 |
|---|---|
| 在线客服 / IM / 短信 / 表单 | **纯文本**。不要 `**加粗**`、`- 列表`、`# 标题`、表格 —— 对方看到的是字面的星号和横杠 |
| 邮件正文 | 纯文本或极简。编号用 `1、2、3`，不用 markdown 语法 |
| 正式信函 / 法律文件 | 按该文书的固有格式，不套 markdown |

**只有终端输出和 .md 文档里 markdown 才有意义。** 这条踩过：给某租车平台客服发了 `**不需要邮寄**`，对方看到一串星号。

## 2. 一次问清

散着问会被一句一句敷衍过去，而且每轮都要等。

- **把所有问题一次列全**，编号
- **用封闭式提问**：能用数字、日期、是/否回答的。「接机收费多少钱」好过「接机贵不贵」
- **给足对方定位所需的信息**：订单号、门店名、日期、型号 —— 让它没有「信息不足所以答不了」的借口
- 先说结论性的一句（我要确认什么），再列问题

## 3. 已发出的消息，小瑕疵一律不处理

**这条是硬规矩。** 消息发出后发现错别字、多余符号、格式没生效：

- **什么都不做**，继续推进对话
- 不重发「修正版」—— 会打断对方正在打字的回复，反而更慢
- 不写「上一条忽略」「刚才发错了」「不好意思」—— 自曝失误，把用户显得不专业

**只有当错误会让对方误解事实时才更正**（发错日期、金额、人名），且直接给正确值，不解释上一条哪里错了。

需要补充信息时，直接说新信息本身。

## 4. 只认书面答复

口头承诺、电话里说的、客服「放心吧」都不算。

- 关键结论必须让对方**用文字写出来**，尤其涉及：钱、证件要求、时间节点、免责与赔付
- 对方绕开不写 → 换一种问法再要一次；连问两次都不肯写进文字，**这件事本身就是结论**（说明它不敢承诺）
- 电话沟通后，补一封邮件到原线程：「Further to my call today with [姓名] at [时间]，确认如下：…」

## 5. 对方含糊就钉住

出现这些词，说明它在留退路，**立刻追问**：

`大部分` `一般来说` `通常` `应该可以` `原则上` `视情况而定` `以门店为准`

追问方式：**把范围收缩到这一单、这一家、这个日期**。
> 「您说『大部分门店支持』，但我需要确定的。能否帮我查一下 XX 店这一家，具体是否支持？」

对方给了范围（如「押金 €1,210–3,630」）→ 追问**上限在什么条件下触发**。

## 6. 隐私边界

- 不主动提供：证件号、卡号、家庭住址、他人个人信息
- 只给完成这件事**必需**的信息（行程日期、订单号、型号）
- 对方索要敏感信息时先问「这一步为什么需要」
- 涉及第三人（家人、同行者）的证件与行程，只给必需的最小集合

## 7. 留证

对外沟通默认按 [luodang](../luodang/SKILL.md) 处理，尤其涉及退款、免责、争议时：

- 关键答复当场存档（文字优先，抓不到再截图）
- 我方发出的邮件要抓 Bcc 副本 —— 🔴 **Bcc 自己的 Gmail 无效**（Gmail 自投去重，收件箱一份都不到）
- 🔴 **而且 Bcc 到一个你没有工具能读取的邮箱，同样等于没有**。
  判据不是「有没有副本」，是「**将来能不能把带 DKIM 的原件导出来**」。
  → **Bcc 目标必须是你有工具能读取并归档的邮箱**（且与发件账号是不同账号，否则被去重）。
  详见 luodang 坑 ①②。
- 对方给了承诺 → 记进案卷文档，写明时间、经手人、原话

## 7A. 🔴 Gmail MCP 的一个陷阱：`send_email` 发不了已有草稿

`mcp__gmail-*__send_email` 是「**新建并发送**」，没有 draftId 参数。
所以「先建草稿 → 逐字核对 → 点发送」这个流程在 MCP 里**走不通**：
发送时必须把正文**重新提交一遍**，等于核对过的那份和发出去的那份是**两次独立输入**。

后果（连发十封长信时踩到）：
- 草稿核对得再仔细，也不能保证发出去的就是那一份。
- 发完草稿还留在草稿箱，不清理就会看起来像「有十封没发」。

✅ **做法**：
1. 正文的**权威源是磁盘上的 .txt/.md 文件**，不是 Gmail 草稿。发送前从文件读，不要凭记忆粘。
2. 发完立刻 `in:sent` 读回核对（主题、收件人、附件、关键段落）。
3. 发完把对应草稿 `modify_email` 加 `TRASH`（🔴 `delete_email` 一律禁用——不可恢复）。
4. 带附件的信，发完要确认 sent 那封里附件真的在（大小对得上）。

顺带：**发信顺序有语义的，必须连发**。例：DSAR → 证件 → 密码，信里写了
"identification ... sent at the same time as this request"，那三封就得几十秒内发完，
否则这句话不实。发完用 sent 的时间戳验一遍间隔。

## 8. 取信息优先抓文字

读页面、读对方回复时：`get_page_text` → `find` → `javascript_tool`，**不要截图**。
理由不只是省 token：截图不可检索、不可 diff、不可引用。
客服对话内容用 JS 读 DOM 文本，不靠截图辨认。

## 9. 语气

- 专业、平实、直接。不谄媚，不道歉，不铺垫
- 不写「麻烦您了」「辛苦了」这类垫话占位 —— 一句「谢谢」放在最后就够
- 被拒绝或推诿时不升温，换个角度再问；要投诉时用事实和条款，不用情绪

## 执行顺序

1. 确认载体 → 定格式
2. 列全问题 → 编号、封闭式
3. 检查隐私边界
4. 发出
5. 对方含糊 → 钉住追问
6. 拿到书面答复 → 存档、记进案卷文档
7. 发现自己有小瑕疵 → **跳过，不处理**
